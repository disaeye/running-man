# Running Man 界面设计数据资料

> 面向产品与界面设计讨论。本文介绍产品能观察到的训练、身体与计划信息，以及这些信息可以支持的用户问题。它不规定页面布局、卡片数量或图表类型；设计师可以据此提出新的信息组织方式。指标是否有实际数值，取决于运动员的同步数据、个人设置与计算所需样本。

## 产品要解决的问题

Running Man 面向习惯自己查看训练数据的跑者。它把 Intervals.icu 的运动记录与身体数据、个人训练参数及本地计算结果放在一起，帮助跑者：

- 判断今天适合怎样训练，并查看建议依据。
- 回顾一段时间练了多少、强度如何、身体能力怎样变化。
- 对照计划与已完成训练，找到差异。
- 了解比赛目标、成绩、生理参数与训练记录之间的关系。

核心体验可以围绕三个时间尺度展开：**今天的决定、近期的训练与恢复、长期的能力变化**。同一个指标可以服务多个问题；例如活动配速可以用于单次复盘、周训练总结和能力趋势。

## 数据的来源与可信边界

产品中的信息大致有三种来源：

1. **运动来源记录**：Intervals.icu 同步或用户导入的活动、分段、运动流、部分健康记录与训练计划。
2. **运动员维护的信息**：个人资料、生理参数、训练区间、目标、比赛成绩、手动活动与力量训练记录。
3. **Running Man 计算结果**：训练负荷、负荷平衡、恢复评分、能力估算、区间汇总、计划质量与建议等。

来源记录与本地计算结果需要在视觉和文案上保持可辨认。某项计算结果可能受样本量、生理参数是否填写、运动数据是否完整等因素影响。设计应给“数据来自哪里、覆盖哪段时间、何时更新、依据是否足够”留出表达空间。数据不足时应明确显示未记录或样本不足，不应让缺失值看起来像零，也不应把估算包装成比赛实绩。

## 数据如何变成设计材料

可以把产品的信息理解为一条从记录到行动的链路：**一次训练与身体记录 → 某段时间的训练画像 → 能力与恢复判断 → 下一步训练选择**。设计师可以沿这条链路组织信息，也可以从跑者每天真实关心的问题出发，重新组合不同来源的资料。

信息并非同等确定。一次活动的开始时间和距离通常是来源记录；TSS 是依据活动和个人训练参数得到的训练负荷；CTL、ATL、TSB 是按时间计算的趋势指标；恢复建议则会使用近期训练与恢复输入形成判断。它们可以出现在同一个体验里，但应让用户看得出哪些是记录、哪些是计算、哪些是建议，并能继续查看相应依据。

设计稿可以为关键数字附带以下语境：统计区间、最近更新时间、来源、计算说明、样本是否充足、与哪个基准比较。每个页面不必同时展示全部语境；当语境会改变用户对数字的理解时，应让它容易找到。

## 可供设计探索的信息领域

### 1. 当天训练决策

**跑者的核心问题：今天做什么、为什么这样安排、什么情况需要调整？**

可以组合当天训练安排、恢复状态与近期负荷。首页目前会呈现就绪判断、恢复评分与部分恢复读数、今日训练建议、训练处方、本周跑量进度、最近一次训练和跑力/生理负荷摘要。设计师可把它们理解为首页可调用的信息素材，不代表必须沿用目前的卡片顺序或版式。

可用信息包括：

- 今日训练：项目、训练类型、距离或时长、训练步骤、目标配速区间、预计训练负荷。
- 当天是否有已完成活动，以及它与原计划的关系。
- 本地恢复评分与恢复建议；来源提供的 readiness、睡眠、HRV、静息心率等恢复线索。
- CTL、ATL、TSB、ACWR 等近期负荷信号，以及近期训练安排。
- 建议的依据、数据日期、样本充分程度。

恢复评分与训练建议属于辅助信息，不应表现成医疗诊断。ACWR 是负荷变化参考，不能用来表达个人受伤概率。当前产品可以生成建议，但尚未实现依据恢复状态自动改写后续课表并取得用户授权。

### 2. 训练周与训练连续性

**跑者的核心问题：训练时间和负荷分配得怎样？哪些天完成了训练，哪些安排需要重新看？**

可从日、周、月范围观察训练执行情况。周视图适合呈现连续的训练节奏，月视图适合让训练量与休息日形成整体印象，选中某一天后再深入到具体课表和活动。可探索把每周训练总量、每日分布、运动类型与计划执行放在同一条阅读路径中。

信息可能包括：

- 跑步、骑行、力量训练等各类活动的次数、距离、时长与训练负荷。
- 按运动类型或训练类型分组的训练量与完成次数。
- 每日训练负荷分布、周总量、月度累计量、爬升。
- 计划课表、已完成活动、完成状态与日期对应关系。
- 计划和实际在距离、时长、心率、RPE、TSS、配速等方面的差异。
- 计划质量、训练阶段与后续负荷预测。

现有日历可以呈现计划与活动的日期对应和部分实际值；系统尚无完整的处方执行评估对象，因此不宜承诺自动判断每个训练步骤完成得是否符合处方。

### 3. 单次活动复盘

**跑者的核心问题：这次训练完成了什么？过程是否符合预期？哪些片段值得回看？**

活动详情可按“整体摘要—训练过程—关键片段—数据依据”的层次探索。摘要可以说清这次活动的类型、距离、时长和主要强度；过程视图可呈现配速、心率或功率随时间的变化；分段或计圈帮助定位节奏变化；区间分布说明训练强度花在哪里。路线、天气或跑步动力学可作为按数据可用性出现的补充线索。

活动详情可支持“这次训练发生了什么、强度分布怎样、表现是否稳定”。可用信息包括：

- 基本记录：运动类型、开始时间、名称、距离、时长、平均与最高心率、平均功率、步频、速度、爬升、卡路里、设备、RPE。
- 来源训练负荷及本地计算的 TSS、rTSS 等结果（适用时）。
- 路线与 GPS 概要、逐时运动流、分段或计圈信息。
- 配速、心率与功率区间分布，标准化功率、坡度修正配速、有氧漂移、效率等可计算指标。
- 天气摘要、跑步动力学相关数据（来源提供时）。
- 收藏、来源、设备和数据完整情况。

不同运动和来源提供的字段不完全相同。没有心率带的活动可能没有心率流；GPS、功率、跑步动力学与天气也可能缺失。界面可围绕“本次活动最值得关注的事实”组织，而不必给每次活动展示相同的指标清单。

### 4. 负荷与恢复

**跑者的核心问题：训练刺激正在累积还是回落？身体恢复线索与训练负荷是否一致？**

可以把训练刺激、近期疲劳与主观/设备恢复信号放在关联视图中。一个可探索的阅读方式是先看一段时间里的负荷走势，再查看某一天或某次训练对走势的影响，最后对照睡眠、HRV、静息心率或主观感受。设计可以让用户切换时间范围、查看变化幅度或追到活动来源；具体图形应由需要解释的关系决定。

- **训练压力分数 TSS / rTSS**：单次与每日训练负荷的估计值，具体算法依赖可用输入与训练参数。
- **CTL**：较长期训练负荷趋势，适合观察训练积累。
- **ATL**：较近期训练负荷趋势，可反映近期负荷变化。
- **TSB**：CTL 与 ATL 的差值，用于理解体能与短期疲劳的关系。
- **ACWR**：近短期负荷与较长周期负荷的比值，用作负荷变化参考；研究解释存在争议，不应单独用于训练或健康结论。
- **恢复相关输入**：HRV、静息心率、睡眠时长、睡眠评分、主观疲劳、酸痛、压力、心情、动机、伤病感受等（取决于来源）。
- **本地恢复评分**：根据可用恢复输入生成，需展示数据是否充分及缺少哪些依据。

时间趋势、训练事件标注、个人基线比较等都可能比孤立的单日数字更有解释力。指标的区间标签和说明应采用项目指标登记中的语义，不应把相同颜色或等级直接泛化为医学风险。

### 5. 能力与比赛表现

**跑者的核心问题：最近能跑到什么水平？哪些变化有成绩或训练证据支持？**

可以帮助跑者理解“目前大致具备什么能力，证据来自哪些记录”。比赛成绩是明确发生过的结果；能力估算是根据训练或比赛样本推得的参考；训练区间是用于安排训练的参数。三者可以相互关联，但应保持含义清楚。设计可以让跑者从某个能力数值追溯到相关活动、比赛成绩或设置参数。

- 最大摄氧量 VO2max（可能来自来源设备）。
- 最大心率 HRmax、乳酸阈值心率 LTHR、阈值配速、VDOT 等估算或个人参数。
- 训练配速区间、心率区间、功率区间及其参数来源。
- 比赛成绩、个人纪录、比赛预测、跑力等级及能力变化趋势。
- 个人最佳距离表现与成绩日期。

估算值、手工设置值、设备同步值和真实比赛成绩的含义不同，应能从呈现方式或说明中区分。估算依赖有效训练或比赛样本，样本不足时应展示限制，不应给出过度确定的结论。

### 6. 训练目标与计划

**跑者的核心问题：我要达到什么目标？接下来如何训练？目前计划与目标之间是什么关系？**

该领域回答“目标还有多远、当前计划如何安排、接下来有哪些关键训练”。目标可关联日期、目标成绩、里程碑与剩余时间；训练计划可关联阶段、周安排、训练步骤和目标区间。日历提供整体节奏，单日详情适合查看具体安排与已完成活动。信息可以从目标概览逐步深入到某一周、某一天和具体训练。

- 目标类型、目标日期、目标成绩或距离、当前状态。
- 里程碑、目标进度、剩余时间及相关比赛成绩。
- 训练阶段、本周课表、未来训练安排、训练处方步骤与配速目标。
- 计划生成所依据的可用训练日、每周训练天数、单次时长等运动员设置。
- 计划调整建议与接受/保留操作。

当前系统支持目标、里程碑、训练阶段、计划生成、日历和部分调整建议。计划历史版本与每次计划决策的完整记录尚未具备；自动调整授权流程也未完整实现。设计时可以呈现当前可用的计划状态，但不应暗示系统保留完整的版本审计记录。

### 7. 身体、健康与生活方式记录

**跑者的核心问题：近期身体状态有哪些变化？哪些记录值得与训练放在一起观察？**

Intervals.icu 数据模型可容纳的健康信息范围较广，是否有真实数据取决于来源是否提供和用户是否记录。此领域适合探索趋势与个人记录，而不是把所有项目堆成一张健康仪表盘。用户可从体重趋势、睡眠记录或恢复自评中选择自己关心的主题；未记录的项目不占据主要视觉位置。

- 体重、体脂率、身高及长期变化。
- HRV、静息心率、睡眠时长、睡眠评分、睡眠质量、睡眠平均心率。
- 血氧、呼吸频率、血压、步数。
- 能量与营养记录：热量、碳水、蛋白质、脂肪、水分状态。
- 主观状态：疲劳、酸痛、压力、心情、动机、伤病感受、备注。
- 生理周期阶段（如来源提供）。

这类信息涉及个人隐私，宜按用户实际目标与数据来源选择呈现范围。当前界面不必把数据模型中所有可容纳字段都放到日常页面；具体适用性和健康解释也需要谨慎处理。

### 8. 力量训练与装备

**跑者的核心问题：力量训练持续做了什么？装备参与了哪些活动、累计使用情况如何？**

力量训练可以补充跑步训练的另一面，信息包括动作、训练日期、组数、重量、次数、肌群、估算最大力量趋势、肌群训练量与分布。动作库是只读参考数据，用户训练记录可以形成时间序列。设计可以探索把单次训练日志与长期训练量联系起来，也可以让动作、肌群和重量成为不同的浏览入口。

装备信息包括跑鞋及累计里程、与活动的关联和装备状态。可用于回答“装备使用了多久、训练由哪些装备完成”。系统有装备与鞋款能力，是否展示更换建议应使用产品已定义的判定依据，避免凭空给出寿命承诺。

### 9. 数据质量与数据来源

**跑者的核心问题：数据更新到什么时候？为什么某个指标没有结果？我是否可以依据它做判断？**

数据状态本身也可以成为产品信息。连接与同步状态适合帮助用户判断数据是否及时；指标的样本量与缺失原因适合解释结论的可靠程度；数据覆盖情况适合解释趋势是否完整。可以将会影响当前判断的信息放在相关视图附近，把排查细节放在数据管理场景。

- 数据源连接状态、最近同步时间、同步是否成功、同步覆盖范围与失败条目。
- 活动与健康数据的覆盖情况、关键字段完整性、待处理的数据质量问题。
- 单项指标的来源、计算方法、更新时间、算法版本或可信程度（适用时）。

这些信息能解释“为什么某项分析没有结果”或“为什么今天看到的数值与之前不同”。在日常首页宜突出会影响当天决策的问题；详细同步记录与覆盖情况可以放在数据管理场景。

## 指标与数据素材详表

以下清单用于让设计师了解可用素材的实际范围。它描述业务含义，不规定这些信息必须同时出现。相同指标可能出现在活动级、日级或周期级视图中；具体能否计算，取决于运动类型、来源字段、训练参数和样本完整性。

### 活动表现与训练过程

| 信息主题 | 可用内容 | 使用时的含义与限制 |
|---|---|---|
| 活动身份 | 运动类型、活动名称、开始时间、来源、设备 | 跑步、室内跑步、越野跑、骑行、室内骑行、健身等；来源与设备可能缺失 |
| 训练量 | 距离、时长、爬升、卡路里、活动次数 | 可看单次、周、月或自定义区间汇总；不同运动的距离不宜无条件合并解释 |
| 速度与节奏 | 平均速度、配速、标准化坡度配速、平均坡度修正配速 | 配速依赖速度数据；坡度修正指标还依赖坡度或海拔样本 |
| 心肺负荷 | 平均/最高心率、心率流、TRIMP、心率区间时间 | 心率设备缺失时可能无值；TRIMP 是来源计算值，语义与 TSS 不同 |
| 功率表现 | 平均功率、来源加权功率、标准化功率、强度系数、效率系数 | 需要功率样本；强度系数依赖 FTP 等个人参数 |
| 跑步动力学 | 步频、步幅、左右平衡 | 由设备或运动流提供；并非每次活动都有 |
| 稳定性线索 | 有氧漂移、配速变化、分段配速/心率/爬升 | 需要足够的稳定运动区间或分段数据，不能对每次活动强行给结论 |
| 强度结构 | 心率、配速、功率区间的时间或占比；活动强度分布 | 适合说明训练时间分布；区间边界来自个人训练区间设置 |
| 路线与环境 | GPS 轨迹、路线摘要、天气温度、体感温度、风、云、降雨/降雪 | 依赖 GPS、天气来源与匹配结果；属于活动上下文，不是训练质量结论 |
| 主观反馈 | RPE（1–10） | 运动员感受记录；与设备测量应区分展示 |
| 训练效果 | TSS、rTSS、每日 TSS | 本地训练负荷计算，输入可能不足；跑步 rTSS 依赖阈值配速 |

### 负荷、恢复与身体指标

| 信息主题 | 指标或记录 | 可帮助观察 |
|---|---|---|
| 负荷积累 | CTL、每日 TSS、周训练负荷 | 较长期负荷与训练量如何累积 |
| 近期疲劳 | ATL、近期活动、短期 TSS | 近期训练刺激是否集中或变化 |
| 负荷平衡 | TSB | 训练积累与近期疲劳之间的差值；需与个人训练上下文一起理解 |
| 负荷变化率 | ACWR | 近 7 日负荷相对近 28 日负荷的变化参考；不用于个人伤病概率判断 |
| 恢复合成 | 本地恢复评分、恢复等级、建议、支持该判断的读数 | 本地计算；需要足够恢复输入，属于训练参考，不是医疗诊断 |
| 心率恢复线索 | HRV、HRV SDNN、静息心率、睡眠平均心率 | 可看单日记录与个人变化；需结合时间范围和设备来源 |
| 睡眠 | 睡眠时长、睡眠评分、睡眠质量 | 睡眠记录可能按天提供，也可能缺少 |
| 身体组成 | 体重、体脂率、身高 | 体重与体脂可看趋势；身高通常来自个人档案 |
| 日常活动 | 步数 | 来源提供时可作为日常活动背景 |
| 呼吸与循环 | 血氧、呼吸频率、收缩压、舒张压 | 来源可能不提供；展示时避免给出未经核实的医疗解读 |
| 营养与水分 | 热量摄入、碳水、蛋白质、脂肪、水分状态 | 记录型输入，不代表产品已提供饮食建议 |
| 主观健康状态 | 疲劳、酸痛、压力、心情、动机、伤病感受、备注 | 主观记录；可支持自我观察，不应自动转化为诊断 |
| 生理周期 | 当前及预测阶段 | 来源提供时记录阶段编码；需尊重隐私并由用户决定是否呈现 |

### 能力、目标与训练安排

| 信息主题 | 可用内容 | 表达时应区分 |
|---|---|---|
| 生理能力 | VO2max、HRmax、LTHR、阈值配速、VDOT | 设备值、个人设置与算法估算的来源不同 |
| 训练区间 | 心率区间、配速区间、功率区间 | 参数可能由运动员设置或由阈值推导；区间用于训练指导 |
| 比赛表现 | 比赛名称、距离类别、日期、完赛时间、PB | 已记录的真实比赛结果；不可与预测结果混为一谈 |
| 比赛预测 | 预测距离/成绩、预测依据、交叉校验信息 | 估算结果，依赖能力数据和有效活动样本 |
| 训练目标 | 目标类型、目标日期、目标成绩/距离、状态 | 由运动员创建和维护 |
| 里程碑 | 里程碑名称、日期、完成状态 | 目标过程中的阶段性记录 |
| 周期与阶段 | 训练阶段名称、日期范围、训练安排 | 阶段结构与日历事件共同构成计划视图 |
| 计划训练 | 训练类别、运动类型、名称、计划时间、距离、TSS、处方步骤、配速范围 | 计划值；缺少参数时部分目标可能为空 |
| 实际训练 | 活动时间、完成状态、实际距离/时长/平均心率/RPE | 实际记录；目前不具备完整的步骤级处方执行评估 |
| 计划质量与预测 | 计划质量信号、减量期信息、强度日安排、预计负荷走势 | 分析结果与规划辅助，不等于实际完成结果 |
| 计划调整 | 调整触发因素、建议内容、接受或保留状态 | 当前有部分调整能力；缺少完整版本历史和授权审计流程 |

### 运动员资料、力量训练与装备

| 信息主题 | 可用内容 | 说明 |
|---|---|---|
| 运动员资料 | 姓名、时区、出生日期、性别、身高、体重目标、偏好运动 | 用户维护；其中部分字段可能为空 |
| 训练设置 | HRmax、静息心率、LTHR、阈值配速、每周训练天数、单次训练时长 | 会影响区间、训练计划或指标计算；可查看当前值与来源 |
| 力量训练动作 | 动作名称、动作类别、肌群等动作库信息 | 动作库是只读参考信息 |
| 力量训练记录 | 训练日期、动作、组、次数、重量、备注 | 适合单次日志、周期训练量与动作趋势 |
| 力量训练分析 | 肌群训练量、肌群分布、e1RM 趋势 | 派生汇总；e1RM 为估算，不是正式测试成绩 |
| 装备 | 鞋款名称、型号、累计里程、关联活动、装备状态 | 累计值依赖活动与装备关联的完整程度 |
| 数据连接 | 来源连接状态、同步时间、同步状态、同步错误与覆盖情况 | 主要用于说明数据新鲜度和排查缺口 |
| 通知 | 通知类别、创建时间、阅读状态、关联信息 | 事件型信息，可用于提示同步失败或目标/训练变化 |

## 页面场景素材

以下内容描述可供设计师挑选的场景与信息关系，不是页面线框，也不要求沿用当前导航结构。

### 每日打开时

可能的阅读顺序：当天结论与训练安排 → 支撑判断的恢复/负荷读数 → 本周已完成和待完成训练 → 最近一次活动 → 能力或目标的长期背景。设计可以压缩成一个聚焦的决定，也可以采用可继续展开的摘要；应让“今天没有安排”“没有恢复记录”“数据刚刚同步失败”等状态都能自然成立。

### 查看训练周时

可以把一周按日期呈现，再配合周训练量、训练次数、距离、时长或负荷摘要。用户选中某天后，可比较计划安排与已记录活动，并进入活动详情。力量训练可以加入同一时间线，也可以作为独立训练类别浏览。周末或周中不应暗示未完成计划必然代表失败，需保留休息日、调整安排与缺数据等解释。

### 复盘一段周期时

可以从“本期发生了什么”进入不同证据：训练量变化、强度分布、负荷趋势、恢复记录、能力变化和目标进展。周期范围可由用户选择；比较对象可以是上一周期、个人近期基线或目标安排，但应明确比较基准。结论文字需要能由展示的数据支撑，并避免将相关变化表述为确定因果。

### 检查目标时

目标概览可以连接目标日期、剩余时间、阶段安排、近期训练和比赛结果。用户可能关心的是进度、当前计划、里程碑或目标是否需要调整，设计可以让这些焦点互相切换。预测成绩应始终以预测身份出现，并展示适用依据或限制。

### 检查身体与恢复时

可围绕用户有持续记录的项目形成个人趋势。单日测量容易受设备和记录条件影响；趋势、个人基线和训练事件上下文可帮助理解变化。敏感信息可采用用户主动进入或自选项目的呈现方式，不必默认在首页全部披露。

### 管理数据时

用户可以关心连接是否有效、数据更新到哪一天、近期同步了哪些活动、哪些活动缺少关键字段，以及某项计算为什么不可用。排障信息应与训练洞察分层：首页只提醒影响判断的重要问题，数据管理场景呈现覆盖、同步运行和具体缺失情况。

## 指标的组织方式建议

以下是供设计讨论的**指标族**，不是必选组件清单。每种视图可以选择少量核心信息，再将其余信息作为深入查看内容。

| 指标族 | 代表信息 | 常见观察问题 |
|---|---|---|
| 训练量 | 次数、距离、时长、爬升、TSS | 这周练了多少？与此前相比怎样？ |
| 训练强度 | 心率、功率、配速、训练区间、RPE | 强度分布是否符合训练目的？ |
| 负荷适应 | CTL、ATL、TSB、ACWR | 负荷与疲劳怎样变化？ |
| 恢复 | HRV、静息心率、睡眠、主观恢复、本地恢复评分 | 今天的训练决定有哪些恢复依据？ |
| 能力 | VO2max、阈值、VDOT、配速区间、个人纪录 | 能力是否发生变化？有哪些记录支持？ |
| 执行 | 计划课次、完成课次、计划与实际差异 | 计划执行到什么程度？ |
| 身体 | 体重、体脂、身体指标趋势 | 身体数据在一段时间内怎样变化？ |
| 质量与来源 | 更新时间、来源、完整性、样本充分程度 | 这个数字从哪里来，能否用于判断？ |

## 设计时需要保留的自由度

- 先决定用户的问题与阅读顺序，再选择指标和图形；本资料不要求所有指标都显示在同一页。
- 可以提出跨领域组合，例如把训练负荷、睡眠和当天课表组成一个决策视图，也可以按训练者的阅读习惯分开呈现。
- 可以探索对比、时间线、分布、日历、活动叙事、异常提示等不同表达。选择应由指标含义和用户任务决定。
- 核心视图与深入分析可以采用不同信息密度；重要数据应能继续追溯到时间范围、来源或单次活动。
- 设计可以提出当前接口尚未提供的表达需求，但请标注为“需要新增数据或计算”，不要把概念稿误认为现有功能。

## 指标组合示例

以下组合用于帮助讨论“哪些数据可以一起解释一个问题”。它们是可能的分析视角，不代表产品已经自动生成每一种结论。

| 想理解的问题 | 可组合的信息 | 设计表达的注意点 |
|---|---|---|
| 今天适合做什么训练？ | 今日处方、就绪度、HRV、睡眠、TSB、近期训练 | 结论旁展示少量关键依据；缺少输入时说明建议依据有限 |
| 这周训练量是否增加？ | 本周与上周距离、时长、活动数、TSS、爬升 | 明确日期范围与比较口径；运动类别差异可能需要分开 |
| 最近负荷变化是否明显？ | 每日 TSS、CTL、ATL、TSB、ACWR | 时间趋势优先于孤立数值；不同指标的含义不可合并成单一“健康分” |
| 轻松跑是否保持轻松？ | 配速、心率、心率区间、RPE、活动时长 | 需要个人区间或以往训练作为参考；路线和天气也可能影响配速 |
| 阈值训练表现怎样？ | 分段配速、心率、功率、目标配速范围、RPE | 计划目标与实际测量应并列区分；运动流不足时不评价稳定性 |
| 能力是否进步？ | 阈值配速、VO2max、VDOT、比赛结果、活动样本 | 显示各项指标的来源与日期；不同方法的变化不一定同步 |
| 训练计划是否适合目标？ | 目标日期、阶段安排、周计划、近期负荷、比赛成绩 | 说明这是规划信息；当前系统没有完整的自动执行质量判定 |
| 体重变化与训练周期是否同时发生？ | 体重时间序列、训练量、活动日期 | 只能表达时间上的并列变化，避免暗示因果 |
| 睡眠变化是否伴随恢复读数变化？ | 睡眠时长/评分、HRV、静息心率、恢复自评、训练日 | 个人记录缺失时不补值；避免医学诊断语气 |
| 跑鞋使用情况如何？ | 鞋款、活动关联、累计里程、活动时间 | 鞋款关联不完整会影响累计里程；更换提示需有明确产品规则 |

## 数据表达的基本规则

- **标明时间范围。** “本周”“近 7 天”“本期”都要有清楚的日期范围或可查看的范围说明。
- **标明单位。** 距离、时长、配速、心率、功率、体重等指标均应有易读单位。
- **保留比较基准。** 增减、进度、区间判断都要说明相对谁比较，例如上周、目标、个人阈值或个人近期基线。
- **保留来源身份。** 来源测量、本地计算、人工设置、预测和建议不能靠同一标签表达。
- **保留缺失含义。** “未记录”“来源未提供”“样本不足”“尚未同步”代表不同情况；不应将它们显示为 0。
- **给估算留出不确定性。** 能力估算、预测成绩、e1RM 和恢复合成评分需要展示适用条件或样本充分程度。
- **避免强行排名。** 目前没有经过验证的用户群体常模或第三方基准数据，界面不应编造百分位、同龄排名或群体对照。
- **让颜色有文字陪伴。** 颜色可帮助识别类别或状态，但不能成为唯一的判断线索。
- **解释重要结论。** 建议、风险提示或变化判断应能指出支撑它的活动、指标、时间范围或数据不足原因。
- **区分事实与因果。** 两项数据同时变化只能说明关联或时间重合，不能直接说其中一项造成另一项变化。

## 页面状态与边界情形

设计资料需要包含这些真实状态，避免只呈现数据齐全的理想画面：

| 状态 | 可能的产品情况 | 可表达的信息方向 |
|---|---|---|
| 尚未接入数据 | 没有连接运动数据源，也没有活动记录 | 解释连接或导入可以带来哪些能力；不显示伪造的图表和指标 |
| 历史不足 | 刚开始记录，训练时间跨度不够 | 展示已经存在的活动，说明哪些趋势或估算还无法形成 |
| 单项缺失 | 活动有配速但没有心率，或有健康记录但无睡眠 | 正常呈现有值信息，并说明缺少的是哪类记录 |
| 样本不足 | 某项估算的输入数量或质量不足 | 明确显示“样本不足”及可补充的数据类型 |
| 同步滞后 | 来源未连接、同步失败或数据日期较旧 | 显示最近成功更新时间及可执行的同步操作 |
| 计划与实际均存在 | 计划训练与活动都能对应到日期 | 并列展示计划和记录，差异使用明确的两类标签 |
| 只有计划 | 未来训练已安排，尚无活动记录 | 保持未来安排的计划身份，不显示成已完成训练 |
| 只有活动 | 记录了活动，但当天没有计划 | 作为自发或手动活动呈现，不推断计划完成情况 |
| 多类训练混合 | 跑步与力量训练出现在同一周期 | 可看总览，同时提供按训练类型查看的路径 |
| 设备或来源更换 | 同一指标的测量设备或提供方发生变化 | 让来源变化可见，避免误读为身体突然变化 |
| 训练参数变化 | 阈值或训练区间被调整 | 允许查看参数当前值和适用时间；参数变化可能影响计算结果 |
| 时区和跨日 | 活动时间接近午夜或用户旅行 | 日期应以运动员设置的时区解释，避免日历归属不一致 |

## 已知产品能力边界

- 数据来源目前以 Intervals.icu 为主，并有文件导入、手动活动及本地记录能力；Strava 支持已废弃。
- 产品提供跑步训练、生理估算、恢复记录、训练计划生成、目标、日历、活动详情、力量训练、装备和数据导出等能力。
- 当前没有完整的训练处方执行评估、计划完整版本历史、用户授权后的自动动态调整流程、定时自动同步入口和产品内历史回填入口。
- 不应添加虚构用户评价、案例、第三方成绩基准或未经核实的训练效果承诺。
